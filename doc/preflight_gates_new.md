# 新增门禁

新增任务（“给某个接口写自动化测试 / 补用例”）的主流程第 2 步是一道**硬门禁**：
在动笔写任何代码之前，先跑查重链、再向用户声明三件事、**等用户确认**。确认之前不写一个字符。

> 项目结构由项目根下的 `.api-autotest/config.json` 声明（不是由 skill 自身安装位置推导）。
> 门禁里说的“落点”就是这份配置里 `paths.api_method_dirs` / `paths.test_case_dirs` 指向的目录。

---

## 第 1 步：跑查重链，拿到事实

在向用户说任何话之前，先把这几件事查清楚：

1. **归一化要测的接口 URL** —— `skill_utils/api_path_match.py` 的 `normalize_path()` → `to_pure_path()`，得到 `pure_path`。
2. **查索引** —— `skill_utils/api_index_db.py` 的 `find_by_path_method(db_path, pure_path, method)`。
   - 命中 → 这条接口**已有**，本次要么跳过、要么是“维护”任务而非“新增”。
3. **未命中 → grep 源码** —— 在接口方法层目录里搜该路径片段，换几种拼写变体再搜一遍。
4. **仍未命中 → 认定为新增。**

把结果整理成两句话：“索引里已有：`<列表>`；本次确认为新的：`<列表>`。”
**空列表也要明说**（“索引里没有，都是新的”）。

---

## 第 2 步：声明三件事

用一段话把下面三项讲清楚（不要只丢一个结论，要带上你**为什么**这么定）：

| 声明项 | 要说什么 | 怎么定 |
|---|---|---|
| **落点** | 接口方法写进哪个文件、用例写进哪个文件 | 按项目既有约定推断；没有可循的约定时，**主动提议一个并说明理由**，不要反问用户该放哪 |
| **方式** | 抓包 / 参考已有 / cURL / 源码分析 | 有信号（用户给了 cURL、项目有相似用例、有后端源码）就自动推断；**彻底没有信号时才弹菜单让用户选** |
| **范围** | 本次做几个接口、几条用例 | 由你提议一个合理范围；范围大到需要拆分时主动提出 |

**给推断，不给填空题。** 门禁的价值是让用户核对你的判断，不是让用户从零填写。
绿地项目里落点本应由 AI 推断——把“文件放哪”甩回给用户是责任错位。

---

## 第 3 步：硬停，等确认

把上面的落点 / 方式 / 范围摆出来后，**停下来**，明确对用户说：

> “以上是本次计划，确认后我就开始写。需要调整的话请直接说。”

**在用户回复确认之前，不要写任何接口方法或用例。** 这是硬停，不是“建议等一下”。

用户可能纠正落点、缩小范围、换方式——收到反馈后按新信息重走第 2 步，再确认。

---

## 确认之后

1. **读规范**（不允许跳过）：必读 `doc/coding_style_guide.md`；按选定的**方式**读对应的 `doc/mode_*.md`。
2. **写代码**：接口方法 + 用例。
3. **pytest 闭环**：用 `skill_utils/pytest_command.py` 的 `build_pytest_command()` 生成命令（**显式传 `shell=`**）并执行；
   失败按 `doc/troubleshooting.md` 定位，循环修复，最多 5 轮。
4. **更新索引**：跑 `tools/scan_api_methods.py` 把新接口补进索引。
5. **输出清单**：接口方法 N 个 / 用例 N 个 / pytest 结果。

---

## 门禁自检

- [ ] 查重链**真的跑了**，不是凭记忆说“应该没有”。
- [ ] 三件事（落点 / 方式 / 范围）都**带理由**地讲清了，而不是只给结论。
- [ ] **明确停住**并等待用户回复，没有自问自答式地“那就开始吧”。
- [ ] 落点确实落在配置声明的目录里。
