# 方式②：参考已有用例

**适用场景**：项目里已经有一批能跑的接口方法与用例，要新增的接口和其中某个**结构相似**
（同一种请求方式、同一套鉴权、同样是列表查询等）。这时最快的做法是**抄一个最近的骨架再改**，
而不是从白纸开始。

> 落点由 `.api-autotest/config.json` 的 `paths.api_method_dirs` / `paths.test_case_dirs` 决定。
> 别处新建目录不算“参考已有”——要参考就先找到已有文件在哪。

---

## 步骤

### 1. 选“骨架”文件

在接口方法层和用例层目录里各挑一个**与被测接口最像**的文件：

- 请求方式相同（都是 POST、都是 GET 列表……）
- 鉴权/登录态使用方式相同
- 断言层级相同（都断言 `body["data"][...]`，或都断言 `body["code"]`）
- 处理了路径参数或分页的，优先参考同样处理了的

用 grep 在接口方法层搜路径片段、搜请求方式（`requests.post` / `api_session.get`）来定位候选。

### 2. 复制骨架，改成本次目标

以骨架文件为模板，逐处替换：

| 要改的 | 从 | 到 |
|---|---|---|
| 函数名 | 骨架的动词+资源名 | 本次接口的动词+资源名 |
| URL | 骨架的路径 | 本次接口的路径（相对路径，不要写 host） |
| 请求方式 | 骨架的 `get`/`post`… | 本次的方法 |
| payload 字段 | 骨架的字段 | 本次接口的字段 |
| 断言 | 骨架的字段断言 | 本次接口的期望值 |

**只改不同的地方，别动骨架里正确的共通部分**（编码声明、docstring 风格、fixture 用法、断言分层）。

### 3. 查重（不能省）

即便“看着像新的”，也必须走查重链：`normalize_path` → `to_pure_path` →
`find_by_path_method(db_path, pure_path, method)` → 未命中再 grep 路径片段。
骨架里可能已经**恰好**实现过这个接口——那样就成了重复。

### 4. 跑起来并两阶段断言

先跑通拿真实返回：

```python
response = get_user_detail(api_session, user_id)
print(response.status_code, response.text)    # 先看清结构
```

确认返回层级与字段后，把 `print` 换成精确断言，并删掉调试代码。

---

## 常见坑

- **抄错了前缀**：骨架用的是项目内工具的前缀写法，本次接口的路径前缀未必一样，确认相对路径拼对。
- **漏改断言字段**：函数改了、URL 改了，断言里还留着骨架的字段名——pytest 会报 KeyError。
- **鉴权方式被抄硬**：骨架如果自己登了一次，要改用项目统一的 `api_session` fixture，别复制一份登录代码。
- **中文乱码**：复制粘贴后文件可能带 BOM 或乱码，写完用 `read_text_utf8()` 或重新 Read 确认。
